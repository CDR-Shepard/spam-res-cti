# AI call context, appointment booking and Salesforce write-back (plan 1D) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** an AI call on a stale Lead or Opportunity should behave like someone who knows the person: "we spoke back in February; are you still thinking about selling the house on Oak Street?" It asks only what Salesforce is missing. It lets the seller book a phone consultation or an in-person walkthrough on a specialist's real calendar. Afterwards it writes the result to Salesforce exactly once: it fills blanks, moves status or stage, records a new "AI Last Call Changes" field, creates the Event, and posts to Chatter. An admin can also run a practice call: a real record and plan, rung to their own test number, with no Salesforce writes.

**Architecture:**
- **Research.** Two deterministic facts are added: the last real contact, in words, and the qualification topics Salesforce is missing. The plan model turns them into `reengagement` and `stillToLearn`.
- **Booking.** At trigger time, `ai_call.place` resolves a specialist and computes free slots from that person's Salesforce Events. It sends them, with a `returning` flag, in the signed trigger.
- **The call.** cti-api renders the slots into a booking section of the agent's instructions and adds a `book_appointment` tool. It stores the booking on `ai_calls`.
- **Write-back.** `ai_call.results`, which already counts each call exactly once, enqueues one `ai_call_writebacks` row in the same transaction. A new `ai_call.writeback` tick then works through steps, each saved before the next starts:
  1. plan the write (describe, fresh read, Claude maps the answers to valid picklist values, a pure builder applies the fill-blank rule and the outcome tables);
  2. the Event, or for a Lead a hold plus a Task;
  3. the PATCH, including the changes field;
  4. a Task;
  5. a Chatter post.
- **Identity.** Every Salesforce write uses the tenant's integration connection, from outreach-api.

**Tech Stack:** TypeScript 5.6 strict ESM, Fastify 4, Drizzle 0.36.4, zod 3, pg-boss 12.30, `@anthropic-ai/sdk` (`claude-sonnet-5-5`), `@cti/salesforce` REST client, React 18 + TanStack Query + Tailwind 4 (outreach-web), vitest. Salesforce metadata lives in `salesforce/force-app`.

**Builds on:** `origin/main` 6d508ba, where plans 1A and 1C and the AI voice engine are live. The spec is `docs/superpowers/specs/2026-10-06-ai-call-context-booking-writeback-design.md`, and it is the source for every mapping table below. The user's decisions are in `.superpowers/sdd/1d-decisions.md`. The 1C plan, `docs/superpowers/plans/2026-10-05-ai-call-campaigns-1c.md`, explains the code this extends.

## Decisions (made while writing this plan)

The product choices that need the user are in the spec's "Decisions for the user". The plan implements each one to its recommendation, behind settings where possible. These are the engineering choices:

1. **Slots are computed at trigger time, not plan time.** Plans are approved hours before a call, and calendars change. The trigger already makes a fresh Salesforce read, so the slot read joins it. Any failure there yields no slots; it never stops the call.
2. **Slots travel as structured data in the signed trigger** (`target.slots`). They never go in the plan text. cti-api renders the words itself, in the seller's time zone (from the number dialed, as `localTimeFor` does).
3. **Write-back runs in outreach-api, not cti-api.** outreach-api holds the integration token and its refresh, the describe cache, the research snapshot (Status or Stage as research saw it), the AI budget, and the exactly-once results counting.
4. **The write plan is frozen on the row** the first time it is computed. A retry never re-runs fill-blank decisions against values the write-back itself wrote.
5. **A table of its own, not 1B's `sf_writes`.** Write-back is a multi-step job per call, not a field outbox. 1B's `sf_writes` is not built, and whenever it is, it takes later migration numbers and never touches these rows.
6. **Practice calls are a third target kind** (`practice`). They are not a test call with a plan, because cti-api must load the real record for the prompt (name, address, notes) while dialing a test number. The row is `is_test = true, practice = true`, so every existing "not for test calls" guard (the Salesforce Task, results counting) already applies. A transfer during a practice call rings the admin who started it, never the record owner.
7. **`appointment_set` is a new outcome.** `ai_calls.outcome` has no CHECK, so no migration is needed. An `end_call` that claims `appointment_set` with no stored booking is recorded as `qualified_callback`.

```ts
export const AppointmentKind = z.enum(['phone', 'walkthrough']);
export const SLOT_ID = /^[pw][1-9]$/;
const SF_USER_ID = /^005[a-zA-Z0-9]{12}(?:[a-zA-Z0-9]{3})?$/;
const IsoInstant = z.string().datetime({ offset: true });
export const IanaZone = z.string().max(64).regex(/^[A-Za-z]+(?:\/[A-Za-z0-9_+-]+){1,2}$/);
export const AppointmentSlot = z.object({
  id: z.string().regex(SLOT_ID),
  kind: AppointmentKind,
  start: IsoInstant,
  end: IsoInstant,
  specialistSfUserId: z.string().regex(SF_USER_ID),
  /** Spoken by the agent ("a quick call with Seth"); cti-api still passes it through oneLine. */
  specialistFirstName: z.string().trim().min(1).max(40).regex(/^[A-Za-z][A-Za-z .'-]*$/).nullable(),
  /** The specialist's zone: business hours are in it. */
  timeZone: IanaZone,
}).strict()
```

- record only what **the seller** said on this call: the `<caller_said>` lines and the agent's saved notes in `<qualification>`;

- `<outcome>`;
- `<qualification>` (JSON, escaped);

**The tables** are the spec's §5.2 and §5.3, row for row. `mode` works like this:
- **`set`:** write the value.
- **`fill`:** write only when the current value is blankish.

Special values:
- `'NOW'` is `now` as an ISO datetime.
- `'CALLBACK'` is `callbackAt`, else the next business day at 10:00 America/Los_Angeles (`zoned.ts`).

- `appointment_set` with a booking gives `appointment`;

**`buildWritePlan` rules, in order:**
1. **The status or stage move** (`Status` or `StageName`). It is applied only when all of these hold:
   - the row has a status;
   - the field is writable;
   - the current value is in `LEAD_FROM` or `OPP_FROM`;
   - for `onlyFromOpen` rows, the current value is in `OPP_OPEN`;
   - the current value equals `researchStatus` (when `researchStatus` is non-null).
   
   Otherwise the field is `skipped` with the reason, and the row's `also` moves still apply. A status move that equals the current value is no change.
2. **`also` moves.** Each value must be valid for its field: in its picklist, a boolean for booleans, a datetime for datetimes. Otherwise the move is skipped as `invalid_value`.
3. **Fill-blanks from `mapped`** (when it is non-null):
   - a field whose current value is blankish (Task 6) gets the mapped value, as a `Change` with why `filled`;
   - a field whose current value is not blankish and differs from the mapped one goes to `Kept`;
   - booleans are written only false → true;
   - a value in `DECLINED_VALUES` is written only over a blank or never-write value;
   - multipicklist values are written joined with `;`.
4. **Appointment:**
   - **Opportunity with result `appointment`:** `appointment = { kind: 'opportunity_event', onBooked: { StageName: 'Appointment Set', Rating__c: 'Hot' } (validated), onConflict: OPP_TABLE.appointment_conflict moves }`. The base patch then carries **no** stage. Task 24 merges `onBooked` or `onConflict` after the Event step.
   - **Lead:** `kind: 'lead_hold'`. `LEAD_TABLE.appointment` is applied in the base patch.
5. **`contactDnc`** is `sfObject === 'Opportunity' && result === 'do_not_call'`.
6. **`patch`** never contains `CHANGES_FIELD`; Task 24 adds it.
7. **`mapped`** is false when `i.mapped === null`, and the changes text says fill-blanks were skipped.

**Known trade-offs called out for the reviewer:**
- **A FeedItem could be posted twice.** If the process dies after Salesforce accepts it and before its id is saved, the retry posts again. A FeedItem Body cannot be filtered in SOQL, so the window is accepted.
- **A slot can be taken between the call and the write-back.** That window is minutes long, and the conflict path records a Task instead of double-booking.
- **A Lead is never converted by the AI** (spec decision 2). Its appointment waits for a person, with a hold on the calendar.
- **A Property Consultation Event cannot be changed or deleted afterwards** without an Appointment Change Request. That is why the Event step looks before it creates, and never edits.
