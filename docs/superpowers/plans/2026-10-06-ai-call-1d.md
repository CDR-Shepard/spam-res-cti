# AI call context, appointment booking and Salesforce write-back (plan 1D) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** an AI call on a stale Lead or Opportunity should behave like someone who knows the person: "we spoke back in February; are you still thinking about selling the house on Oak Street?" It asks only what Salesforce is missing. It lets the seller book a phone consultation or an in-person walkthrough on the appointment owner's real calendar (Grant Golden, who distributes them). Afterwards it writes the result to Salesforce exactly once: when a Lead books, it converts the Lead the way the team does; then it fills blanks, moves status or stage, records a new "AI Last Call Changes" field, creates the Event, and posts to Chatter. An admin can also run a practice call: a real record and plan, rung to their own test number, with no Salesforce writes.

**Architecture:**
- **Research.** Two deterministic facts are added: the last real contact, in words, and the qualification topics Salesforce is missing. The plan model turns them into `reengagement` and `stillToLearn`.
- **Booking.** At trigger time, `ai_call.place` takes the appointment owner (the first active user on the tenant's list; default Grant Golden) and computes free slots from that person's Salesforce Events. It sends them, with a `returning` flag, in the signed trigger.
- **The call.** cti-api renders the slots into a booking section of the agent's instructions and adds a `book_appointment` tool. It stores the booking on `ai_calls`.
- **Write-back.** `ai_call.results`, which already counts each call exactly once, enqueues one `ai_call_writebacks` row in the same transaction. A new `ai_call.writeback` tick then works through steps, each saved before the next starts:
  0. for a Lead that booked: convert it (SOAP `convertLead`, owner = the appointment owner, status Qualified), then carry the Lead's consent, language, dialer and lead-manager values onto the new Opportunity; every later step targets that Opportunity;
  1. plan the write (describe, fresh read, Claude maps the answers to valid picklist values, a pure builder applies the fill-blank rule and the outcome tables);
  2. the Event (on an Opportunity, owned by the appointment owner); only when a conversion is refused for good, a calendar hold plus a "convert and book" Task instead;
  3. the PATCH, including the changes field;
  4. a Task;
  5. a Chatter post.
- **Identity.** Every Salesforce write uses the tenant's integration connection, from outreach-api: whatever Salesforce user that connection signed in as. Nothing in the plan depends on which user that is.

**Tech Stack:** TypeScript 5.6 strict ESM, Fastify 4, Drizzle 0.36.4, zod 3, pg-boss 12.30, `@anthropic-ai/sdk` (`claude-sonnet-5-5`), `@cti/salesforce` REST client (plus one SOAP call, `convertLead`), React 18 + TanStack Query + Tailwind 4 (outreach-web), vitest. Salesforce metadata lives in `salesforce/force-app`.

**Builds on:** `origin/main` 6d508ba, where plans 1A and 1C and the AI voice engine are live. The spec is `docs/superpowers/specs/2026-10-06-ai-call-context-booking-writeback-design.md`, and it is the source for every mapping table below. The user's decisions are in `.superpowers/sdd/1d-decisions.md`. The 1C plan, `docs/superpowers/plans/2026-10-05-ai-call-campaigns-1c.md`, explains the code this extends.

## Decisions (made while writing this plan)

The product choices that need the user are in the spec's "Decisions for the user". The plan implements each one to its recommendation, behind settings where possible. These are the engineering choices:

1. **Slots are computed at trigger time, not plan time.** Plans are approved hours before a call, and calendars change. The trigger already makes a fresh Salesforce read, so the slot read joins it. Any failure there yields no slots; it never stops the call.
2. **Slots travel as structured data in the signed trigger** (`target.slots`). They never go in the plan text. cti-api renders the words itself, in the seller's time zone (from the number dialed, as `localTimeFor` does).
3. **Write-back runs in outreach-api, not cti-api.** outreach-api holds the integration token and its refresh, the describe cache, the research snapshot (Status or Stage as research saw it), the AI budget, and the exactly-once results counting.
4. **The write plan is frozen on the row** the first time it is computed. A retry never re-runs fill-blank decisions against values the write-back itself wrote.
5. **A table of its own, not 1B's `sf_writes`.** Write-back is a multi-step job per call, not a field outbox. 1B's `sf_writes` is not built, and whenever it is, it takes later migration numbers and never touches these rows.
6. **Practice calls are a third target kind** (`practice`). They are not a test call with a plan, because cti-api must load the real record for the prompt (name, address, notes) while dialing a test number. The row is `is_test = true, practice = true`, so every existing "not for test calls" guard (the Salesforce Task, results counting) already applies. A transfer during a practice call rings the admin who started it, never the record owner.
7. **`appointment_set` is a new outcome.** `ai_calls.outcome` has no CHECK, so no migration is needed. An `end_call` that claims `appointment_set` with no stored booking is recorded as `qualified_callback`.
8. **One appointment owner, not a rotation.** The user decided every AI-booked appointment goes to Grant Golden, who distributes them. The settings keep an ordered list; the first active user on it owns every slot and Event. There is no owner-first rule and no rotation.
9. **Convert with SOAP, not Apex.** `convertLead()` is a standard SOAP API call; Salesforce accepts an OAuth access token as the SOAP session id, and the connection's `api` scope covers the SOAP API. That avoids deploying Apex (and its test class) to a production org that already has failing tests. Readiness (Task 27) proves it per tenant with a read-only SOAP `getUserInfo()` and a check of the Convert Leads permission; if either fails, a booked Lead takes the fallback path instead.
10. **Convert first, then everything else on the new Opportunity.** Conversion is its own step (Task 24) that runs before the plan step. The plan, the Event, the fields, the Task and the Chatter post then target the new Opportunity, exactly as for an Opportunity call, so there is one write path. The fallback (hold + Task on the Lead) is used only when Salesforce refuses the conversion for good.

 *  the SessionHeader carries the current access token. A fault `INVALID_SESSION_ID` (or HTTP 401) refreshes the token once and retries;
 *  a second one throws SalesforceAuthError. Returns the raw response XML and status. 30 s timeout, like every request. */
async soap(bodyXml: string, opts?: { signal?: AbortSignal }): Promise<{ status: number; xml: string }>;
// convert-lead.ts
export interface ConvertLeadRequest {
  leadId: string; convertedStatus: string; ownerId: string;
  opportunityName: string;          // ≤ 120 chars
  sendNotificationEmail: boolean;   // false for the AI
}
export type ConvertLeadResult =
  | { success: true; leadId: string; accountId: string; contactId: string; opportunityId: string }
  | { success: false; errors: Array<{ statusCode: string; message: string; fields: string[] }> };
export function convertLeadEnvelope(r: ConvertLeadRequest): string;      // pure; every value XML-escaped
export function parseConvertLeadResponse(xml: string): ConvertLeadResult; // pure; a SOAP fault → throws SalesforceApiError(code)
export async function convertLead(client: SalesforceClient, r: ConvertLeadRequest): Promise<ConvertLeadResult>;

**Known trade-offs called out for the reviewer:**
- **A FeedItem could be posted twice.** If the process dies after Salesforce accepts it and before its id is saved, the retry posts again. A FeedItem Body cannot be filtered in SOQL, so the window is accepted.
- **A slot can be taken between the call and the write-back.** That window is minutes long, and the conflict path records a Task instead of double-booking.
- **SOAP for one call.** `convertLead` is the only SOAP use; readiness proves it per tenant, and a tenant whose user cannot use it gets the fallback, never a stuck row.
- **Record types on conversion** are Salesforce's defaults for the converting user. They are shown, not forced, because changing an Opportunity's record type after insert would skip the org's insert flows.
- **A Property Consultation Event cannot be changed or deleted afterwards** without an Appointment Change Request. That is why the Event step looks before it creates, and never edits.
