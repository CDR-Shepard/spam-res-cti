# Test a record: preview the AI's approach, then run it to your phone or in the browser (plan 1E) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** an admin pastes a Salesforce Lead or Opportunity Id (or its Lightning URL) into a **Test a record** page and sees "how I'm going to approach this call": the last real contact and re-engagement line, what is still to learn, the opener, the exact plan text the voice agent gets, the appointment times it would offer, the consent status, and anything that would stop the agent being given the plan. The admin can then run the call: **Ring my phone** (an admin test number) or **Talk in browser** (the AI rings the admin's browser tab, which answers on its own). After the call the page shows the outcome, the summary, what the AI learned, "would have booked …", the transcript and, on request, "would have written to Salesforce: …". Nothing is ever written to Salesforce.

**Architecture:**
- **Preview (outreach-api).** `POST /api/record-tests` parses the input, checks limits and budget, inserts an `ai_record_tests` row (`running`) and answers 202. In the same process it then runs the existing 1C/1D pieces with no campaign:
  - `researchRecord`, `planFacts`, `buildCallPlanPrompt`, `CallPlanModel.plan` and `withPlanFacts`;
  - `renderPlanForAgent`;
  - the 1D practice slot offer.

  It stores the result. The page polls `GET /api/record-tests/:id`.
- **Run, phone.** The 1D `practice` target, unchanged.
- **Run, browser.**
  - A new internal route has cti-api mint an **incoming-only** Twilio Voice token for a per-run identity, `aitest_<admin>_<nonce>`. outreach-api relays it, and the page registers a Voice JS `Device`.
  - A new target kind, `practice_browser`, makes cti-api place the same practice call to `client:<identity>`, through the same `startAiCall` → `placeCall` → `<Connect><Stream>` path. The differences: AMD off, a browser branch in the gate, and no `calls` row.
  - The page auto-accepts the incoming call.
- **After.** The test's calls are joined to `ai_calls` for the outcome, summary, qualification and appointment. Transcripts open through the practice transcript loader. An optional dry run composes the 1D write plan (describe, GET, mapping model, pure builder and renderers) without a single write.

**Tech Stack:** TypeScript 5.6 strict ESM, Fastify 4, Drizzle 0.36.4, zod 3, `@anthropic-ai/sdk` (`claude-sonnet-5-5`), `@cti/salesforce` (reads only), the `twilio` Node SDK (cti-api), `@twilio/voice-sdk` ^2.12.3 (new in outreach-web), React 18 + TanStack Router/Query + Tailwind 4, vitest.

**Builds on:** `feat/ai-call-1d` (stacked; 1D is still taking review fixes in another worktree). The spec is `docs/superpowers/specs/2026-10-06-ai-call-test-a-record-design.md`, and its §4–§8 are the source for every rule below. The 1D plan, `docs/superpowers/plans/2026-10-06-ai-call-1d.md`, explains the practice call this extends.

## Decisions (made while writing this plan)

1. **Browser calls: the AI calls the browser.** cti-api places the practice call to `client:<identity>` through the same path as every AI call. The rejected alternatives were:
   - a TwiML App outgoing call (it would go through cti-web's dial route and need an outgoing grant);
   - browser-to-OpenAI WebRTC (it bypasses the bridge and tools);
   - our own audio WebSocket (a second audio stack).

   Spec §5.1 gives the reasons.
2. **A new target kind, `practice_browser`,** rather than an optional field on `practice`:
   - zod's `discriminatedUnion` needs plain objects, so "exactly one of `to`/`clientIdentity`" cannot be refined inside it;
   - a new kind makes every exhaustive switch (1D D-2) fail to compile until it is handled.
3. **An incoming-only token, minted by cti-api, one per run.** cti-api already holds the Twilio API key. A fresh identity per run means no refresh logic and no cross-ringing with `rep_…` softphones.
4. **Preview runs in-process after a 202, and the page polls.** The plan model can take a minute, and a synchronous request would sit open behind the proxy. A restart mid-preview leaves a `running` row, which reads as `failed: interrupted` after 6 min; nothing rewrites it.
5. **New tables, not `ai_practice_calls`.** Its campaign, enrollment, version and number columns are NOT NULL, and 1D (owner of 0056/0057) is still in review.
6. **Limits are counted in Postgres under `pg_advisory_xact_lock`,** per admin. They survive restarts and replicas, and two quick clicks cannot both pass. No per-route limiter exists today.
7. **A browser leg writes no `calls` row.** No phone was dialed, so there is nothing for the cap, the ceiling or contact history to count. Its caller ID is a read-only pick of the org's `ai_pool` (no DID dial is claimed).
8. **The dry run is on request and optional** (Task 11). It costs one mapping call, and the rest of 1E does not depend on it.

```ts
export const PREVIEWS_PER_HOUR = 10;
export const PREVIEWS_PER_DAY = 40;
export const CALLS_PER_HOUR = 6;
export const PREVIEW_STALE_MS = 6 * 60_000;
export const UNANSWERED_CALL_MS = 2 * 60_000;
export type LimitRefusal =
  | { code: 'RATE_LIMITED'; retryAt: Date }
  | { code: 'PREVIEW_RUNNING' }
  | { code: 'CALL_IN_PROGRESS' }
  | { code: 'AI_BUDGET_SPENT' };
/** In one transaction: pg_advisory_xact_lock(hashtext('rtest:' || userId)), the counts, then `insert` when allowed. */
export async function withPreviewLimit<T>(db: Db, a: { orgId: string; userId: string; now: Date; budgetMicros: number }, insert: (tx: Db) => Promise<T>): Promise<{ ok: true; value: T } | { ok: false; refusal: LimitRefusal }>;
export async function withCallLimit<T>(db: Db, a: { orgId: string; userId: string; now: Date }, insert: (tx: Db) => Promise<T>): Promise<{ ok: true; value: T } | { ok: false; refusal: LimitRefusal }>;
```

**How each limit is counted:**
- **Previews running:** a row of this admin with `status = 'running'` and `created_at > now - PREVIEW_STALE_MS`.
- **Previews per hour:** this admin's rows in the last hour. `retryAt` is the oldest row in that window + 1 h.
- **Previews per day:** the org's rows since the UTC day start (`utcDay`). `retryAt` is the next UTC midnight.
- **The budget:** `spentTodayMicros >= budgetMicros`.
- **Live calls:** this admin's `ai_record_test_calls` either joined to an `ai_calls` row whose status is not `completed`, `failed`, `blocked` or `transferred` and was created in the last hour (a stuck row stops blocking), or with a null `ai_call_id` and `created_at > now - UNANSWERED_CALL_MS`.
- **Calls per hour:** this admin's calls in the last hour.
